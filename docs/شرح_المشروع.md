# مشروع رفقة بلاد الحرمين — شرح قاعدة البيانات والربط والمراجعة النهائية

هذا الملف يشرح كيف صُممت قاعدة بيانات المشروع، وكيف يتصل بها الموقع، وما الذي كان
موجوداً قبل المراجعة وما الذي تغيّر ولماذا. كل ما فيه مأخوذ من الملفات النهائية
الموجودة في هذا المستودع (`website/` و `mobile_app/`)، ويمكن فتح أي ملف مذكور
والتحقق منه مباشرة.

---

## 1. فكرة المشروع ومستخدموه

نظام لإدارة حملة حج، فيه ثلاثة أنواع من المستخدمين، ولكل نوع رقم عضوية يبدأ
ببادئة مختلفة:

| النوع | بادئة رقم العضوية | أين بياناته | ماذا يرى |
|---|---|---|---|
| الحاج / الحاجة | `100xxx` | جدول `pilgrims` | ملفه، سكنه، جدوله، الخدمات، التقييم، المحادثة، التنبيهات |
| المشرف المتخصص | `500xxx` | جدول `supervisors` | حجاج قسمه وتخصصه، مهامه، طلبات الخدمة، القيود المالية، المحادثة |
| المشرف العام | `5000` | جدول `supervisors` (وظيفة «مشرف عام») | كل التخصصات في القسم الذي يختاره عند الدخول |
| مدير الحملة | `300xxx` | جدول `campaigns` | كل شيء: الحجاج، التوزيع، المشرفون، القيود، التقييمات، الصلاحيات، ملف الحملة |

القسم (رجال / نساء) مهم في كل مكان: الحاج يُصنَّف بقسمه من حقل `gender`،
والمشرف المتخصص له قسم ثابت في `gender_section`، والمشرف العام يختار القسم
عند تسجيل الدخول.

## 2. لماذا هذه الجداول بالذات؟

نقطة البداية كانت ملف SQL أصلي فيه 9 جداول:
`campaigns, supervisors, pilgrims, services, service_provisions, ratings, permissions, notifications, chat_rooms`.

القاعدة التي اتُّبعت في المراجعة: **كل شاشة في الموقع تعرض بيانات أو تحفظها
لازم يكون لها مكان في قاعدة البيانات، وكل حقل في نموذج لازم يقابله عمود**.
بناءً عليها:

- **أُبقيت الجداول التسعة كلها** ولم يُحذف أي عمود منها إلا عموداً واحداً
  (`chat_rooms.pilgrim_id`) يُشرح سببه لاحقاً.
- **أُضيفت 4 جداول** لأن شاشات موجودة فعلاً كانت بلا جدول:
  - `jobs` — جدول الوظيفة (من الرسم اليدوي: وظيفة Id / مسمى وظيفي / الصلاحية)
  - `expenses` — القيود المالية (صفحة `expenses.html` ولوحة الإدارة ولوحة المشرف)
  - `messages` — الرسائل (صفحة `chat.html` ولوحة المشرف)
  - `supervisor_tasks` — مهام المشرف وحالتها (لوحة المشرف)
- **أُضيفت أعمدة** إلى جداول موجودة لتغطية حقول النماذج (شرحها في القسم 3).

المحرّك `InnoDB` والترميز `utf8mb4_unicode_ci` لكل الجداول، لأن InnoDB هو الذي
يفرض المفاتيح الأجنبية، و `utf8mb4` هو الذي يحفظ العربية والرموز بشكل سليم.

## 3. وظيفة كل جدول وأهم أعمدته

### `campaigns` — الحملة
صف واحد لكل حملة. يُستخدم أيضاً لتسجيل دخول مدير الحملة.

| العمود | معناه |
|---|---|
| `campaign_id` (PK) | رقم الحملة، وهو رقم عضوية المدير (مثل `30089`) |
| `campaign_name`, `license_number`, `phone`, `location`, `extra_info` | بيانات الحملة الأصلية |
| `company_name`, `manager_name`, `manager_email`, `manager_phone`, `price_per_person`, `start_city`, `start_date` | **مضافة** — حقول نموذج `campaign-profile.html` |
| `password_hash` | **مضاف** — كلمة مرور المدير مشفّرة |

### `jobs` — الوظيفة  (جدول جديد)
| العمود | معناه |
|---|---|
| `job_id` (PK) | وظيفة Id |
| `job_title` | المسمى الوظيفي كما يظهر في الشاشات |
| `permission_level` | الصلاحية (وصف نطاق عمل الوظيفة) |
| `role_key` | مفتاح قصير بالإنجليزية يستخدمه الكود: `general / medical / crowd / catering / housing` |

الصفوف الخمسة: مشرف عام، الموظف الصحي، موظف الحشود والتنقل، موظف الإعاشة
والأطعمة، موظف السكن وخدمة الحجاج.

### `supervisors` — المشرفون
| العمود | معناه |
|---|---|
| `supervisor_id` (PK) | رقم العضوية (`5000`, `500101` …) |
| `campaign_id` (FK) | الحملة التي يتبعها |
| `job_id` (FK) | **مضاف** — وظيفته من جدول `jobs` |
| `gender_section` | **مضاف** — `men` / `women` / `all` (الأخيرة للمشرف العام) |
| `name`, `phone`, `email`, `password_hash` | بياناته وكلمة مروره المشفّرة |

### `pilgrims` — الحجاج
| العمود | معناه |
|---|---|
| `pilgrim_id` (PK) | رقم العضوية، يبدأ من `100101` ويتزايد تلقائياً |
| `campaign_id` (FK), `supervisor_id` (FK) | الحملة والمشرف المسؤول |
| `booking_number`, `name`, `id_or_passport`, `phone`, `nationality`, `age`, `city`, `package_type`, `gathering_point`, `tent_number`, `bed_number`, `password_hash` | الأعمدة الأصلية |
| `gender`, `email`, `marital_status`, `chronic_conditions` | **مضافة** — يرسلها نموذج `register.html` ولم يكن لها أعمدة |
| `camp_id` | **مضاف** — رقم المخيم الذي تسنده صفحة `assign-pilgrims.html` |
| `created_at` | **مضاف** — تاريخ التسجيل |

### `services` — أنواع الخدمات
`service_id` (PK)، `service_name`، `description`، `service_type` (يطابق `role_key` في `jobs` حتى يصل الطلب للمشرف المختص)، `service_datetime`، `service_location`، `status`.
فيه 7 صفوف: طبية، تفويج، إعاشة، سكن، أمتعة مفقودة، وخدمتان عامتان تظهران في نافذة
«تقييم الخدمات».

### `service_provisions` — طلبات الخدمة
كل صف = حاج طلب خدمة. `pilgrim_id` (FK)، `service_id` (FK)، `supervisor_id` (FK **مضاف**)،
`request_number` و `details` (**مضافان** لأن جدول الطلبات في لوحة المشرف يعرضهما)،
`provision_date`، `provision_time`، `status`.

### `ratings` — التقييمات
| العمود | معناه |
|---|---|
| `rating_id` (PK) | |
| `pilgrim_id` (FK) | **مضاف** — من قيّم |
| `service_id` (FK) | **مضاف** — أي خدمة قُيِّمت (نافذة «تقييم الخدمات» في `services.html`) |
| `provision_id` (FK، اختياري) | طلب محدد إن كان التقييم على طلب بعينه |
| `stars` | من 1 إلى 5 — مع قيد `CHECK (stars BETWEEN 1 AND 5)` |
| `comment`, `rating_date` | |

### `permissions` — تصاريح الحج
**تنبيه تسمية مهم:** هذا الجدول في الملف الأصلي يمثّل *تصريح الحج* الخاص بالحاج
(مرتبط بحملة وحاج وفيه `permission_name` = رقم التصريح). ليس جدول صلاحيات النظام.
صلاحيات النظام صارت في جدول `jobs`.

### `expenses` — القيود المالية  (جدول جديد)
`expense_id` (PK)، `campaign_id` (FK)، `supervisor_id` (FK — من سجّل القيد)،
`description`، `amount`، `category`، `expense_date`، `receipt_file` (اسم ملف الفاتورة داخل
`uploads/`)، `status` (`مرحّل` ثم `معتمد` بعد اعتماد المدير)، `created_at`.

### `supervisor_tasks` — مهام المشرف  (جدول جديد)
`task_id` (PK)، `supervisor_id` (FK)، `title`، `description`، `status`.
زر «تحديث» في جدول المهام بلوحة المشرف يغيّر `status` هنا.

### `notifications` — التنبيهات
الجدول الأصلي كان فيه المُرسِل فقط (`supervisor_id`) ولا يوجد مستقبِل. أُضيف:
`campaign_id`، `pilgrim_id` (تنبيه شخصي)، `target_role` (`pilgrim / supervisor / campaign / all`)،
`target_section` (`men / women / all`)، `icon`، `is_read`. بهذا يستطيع الخادم أن يرجع
لكل مستخدم التنبيهات الموجهة لدوره وقسمه أو له شخصياً.

### `chat_rooms` و `messages` — المحادثة
`chat_rooms` الأصلي كان فيه `room_id` و `pilgrim_id` و `message_type` فقط — لا نص
رسالة ولا مرسل ولا وقت، وربطه بحاج واحد يمنع أن تكون الغرفة جماعية.
صار: `room_id` (PK)، `campaign_id` (FK)، `room_name`، `section`، `staff_only`
(غرفة المشرفين والإدارة لا تظهر للحاج)، `message_type`.
وجدول `messages` الجديد: `message_id` (PK)، `room_id` (FK)، `sender_type`، `sender_id`،
`sender_name`، `message_text`، `sent_at`.

## 4. العلاقات والمفاتيح

المخطط الكامل في `docs/er_diagram.png` (ومصدره `docs/er_diagram.mmd`).

```
campaigns 1 ──── N supervisors N ──── 1 jobs
    │                 │
    │                 └── 1 ──── N pilgrims ──── N permissions
    │                                │
    │                                ├── 1 ──── N service_provisions N ──── 1 services
    │                                │                 │                        │
    │                                └── 1 ──── N ratings ◄─────────────────────┘
    ├── 1 ──── N expenses  (N ──── 1 supervisors)
    ├── 1 ──── N notifications
    └── 1 ──── N chat_rooms 1 ──── N messages
supervisors 1 ──── N supervisor_tasks
```

**المفتاح الأساسي (PK):** عمود `*_id` في كل جدول. في `pilgrims` و `supervisors`
و `campaigns` هو نفسه رقم العضوية الذي يُدخله المستخدم في شاشة الدخول.

**المفاتيح الأجنبية (FK) وسلوك الحذف:**

| العلاقة | عند حذف الأب |
|---|---|
| `supervisors.job_id → jobs` | `SET NULL` (المشرف يبقى بلا وظيفة) |
| `pilgrims.supervisor_id → supervisors` | `SET NULL` (الحاج يبقى ويُعاد إسناده) |
| `service_provisions.pilgrim_id → pilgrims` | `CASCADE` (طلبات الحاج تُحذف معه) |
| `ratings.pilgrim_id → pilgrims` | `CASCADE` |
| `ratings.service_id → services` / `provision_id → service_provisions` | `SET NULL` |
| `messages.room_id → chat_rooms` | `CASCADE` |
| `expenses.supervisor_id → supervisors` | `SET NULL` (القيد المالي لا يختفي) |
| `pilgrims.campaign_id` و `supervisors.campaign_id → campaigns` | بدون حذف تلقائي (`ON UPDATE CASCADE` فقط) |

قاعدة الاختيار: السجل التابع الذي لا معنى له بدون الأب يُحذف معه (`CASCADE`)،
والسجل الذي له قيمة مستقلة يبقى ويُفرَّغ الرابط فقط (`SET NULL`).

## 5. كيف يتصل الموقع بقاعدة البيانات

```
المتصفح (HTML + JS)  ──fetch──►  website/api/*.php  ──PDO──►  MySQL (rafqa_haramain)
                     ◄──JSON──                      ◄────────
```

- الصفحات تبقى `.html` كما صُممت، وكل صفحة تحمّل `js/api.js`.
- `api.js` فيه دالتان أساسيتان: `API.get(file, action)` و `API.post(file, action, data)`
  ترسلان الطلب إلى ملف PHP داخل `website/api/` وترجعان JSON.
- بيانات الاتصال كلها في ملف واحد `api/config.php` (ويُقرأ في `api/db.php`).
  هذا الملف يُنفَّذ على الخادم فقط ولا يصل للمتصفح أبداً، ولهذا لا توجد أي كلمة
  مرور في ملفات HTML أو JavaScript.
- الاتصال عبر PDO مع `ATTR_EMULATE_PREPARES = false` حتى تكون الاستعلامات المجهّزة
  حقيقية، و `charset=utf8mb4` في سلسلة الاتصال.
- ملف `.htaccess` داخل `api/` يمنع فتح `config.php` و `db.php` و `helpers.php`
  مباشرة من المتصفح، وملف `.htaccess` داخل `uploads/` يمنع تنفيذ أي PHP هناك.

### ملفات الـ API ووظائفها

| الملف | المسؤولية |
|---|---|
| `auth.php` | `login` / `logout` / `me` — التحقق من كلمة المرور بـ `password_verify` وفتح جلسة |
| `pilgrims.php` | `list`, `get`, `register`, `update`, `delete` |
| `supervisors.php` | `list`, `profile`, `jobs` |
| `assignments.php` | `list`, `assign`, `auto`, `remove` — توزيع الحجاج (يحدّث `supervisor_id` و `camp_id` في `pilgrims`) |
| `expenses.php` | `list`, `add` (مع رفع الفاتورة), `approve`, `delete` |
| `services.php` | `list`, `requests`, `request`, `update_status` |
| `ratings.php` | `list`, `add` |
| `tasks.php` | `list`, `update_status` |
| `notifications.php` | `list`, `mark_read`, `mark_all_read`, `send` |
| `chat.php` | `rooms`, `messages`, `send` |
| `campaign.php` | `get`, `update`, `stats` |
| `helpers.php` | قراءة المدخلات والتحقق منها، الجلسة، `require_user([...])` للصلاحيات، رفع الملفات |

### الصلاحيات في الخادم
كل عملية تبدأ بـ `require_user([...])` التي تتأكد أن المستخدم مسجّل دخوله وأن دوره
مسموح. أمثلة من الكود:
- `pilgrims.php?action=list` للمشرف ومدير الحملة فقط؛ الحاج يحصل على `403`.
- الحاج لا يفتح إلا ملفه: `if ($u['role']==='pilgrim' && $id !== $u['id']) fail(403)`.
- المشرف المتخصص يرى حجاج قسمه فقط، والقسم يُؤخذ من الجلسة لا من الطلب،
  فلا يفيده تمرير `section=women` يدوياً.
- `chat.php` يرفض غرفة `staff_only` للحاج حتى لو عرف رقمها.

## 6. رحلة البيانات: من النموذج إلى الجدول ثم إلى الشاشة

### مثال 1 — تسجيل حاج جديد (`register.html` → `pilgrims` → لوحة الإدارة)

1. الحاجة تعبّئ النموذج وتضغط «إنشاء الحساب».
2. JavaScript يجمع الحقول:
   ```javascript
   const data = Object.fromEntries(new FormData(registerForm).entries());
   const res  = await API.post('pilgrims.php', 'register', data);
   ```
3. `api/pilgrims.php` → `register_pilgrim()` يتحقق: الاسم وكلمة المرور ورقم الهوية
   والجوال مطلوبة، كلمة المرور ≥ 6، البريد بصيغة صحيحة، العمر 1–120، رقم الحملة
   موجود في `campaigns`، رقم الهوية غير مكرر.
4. يُنفَّذ `INSERT INTO pilgrims (...) VALUES (?,?,...)` وكلمة المرور تُخزَّن بـ
   `password_hash(..., PASSWORD_DEFAULT)`.
5. يرجع `pilgrim_id` الجديد (مثل `100203`) ويُعرض للحاجة كرقم عضويتها.
6. عند فتح مدير الحملة نافذة «عرض الحجاج» يستدعي `pilgrims.php?action=list`
   فيظهر الصف الجديد فوراً لأنه صار سجلاً حقيقياً.

### مثال 2 — تقييم خدمة (`services.html` → `ratings` → لوحة الإدارة)

1. قائمة الخدمات في النافذة تُبنى من `services.php?action=list`.
2. الحاج يختار الخدمة والنجوم ويكتب ملاحظة، فيُرسَل:
   `API.post('ratings.php', 'add', { service_id, stars, comment })`.
3. `add_rating()` يتأكد أن النجوم 1–5 وأن الخدمة موجودة، ثم
   `INSERT INTO ratings (pilgrim_id, service_id, provision_id, stars, comment)`.
4. في لوحة الإدارة، `ratings.php?action=list` يربط `ratings` بـ `pilgrims` و `services`
   ويحسب المعدل، فيظهر التقييم باسم الحاج وموضوع الخدمة.

### مثال 3 — اعتماد قيد مالي

`expenses.html` (مشرف) يضيف القيد بحالة `مرحّل` → يظهر في لوحة المدير →
زر «اعتماد نهائي» يرسل `expenses.php?action=approve` →
`UPDATE expenses SET status='معتمد' WHERE expense_id=? AND campaign_id=?` →
تُعاد قراءة القائمة فتظهر الحالة الجديدة، وتبقى محفوظة بعد إعادة التحميل أو من أي جهاز آخر.

## 7. الوضع قبل المراجعة، وما تغيّر، ولماذا

### الموقع قبل المراجعة
- 21 صفحة HTML/CSS/JS ثابتة **بدون أي Backend**، وملف SQL غير مرتبط بها وفارغ من البيانات.
- تسجيل الدخول يقبل أي كلمة مرور طولها 6 خانات، والدور يُستنتج من بادئة الرقم فقط.
- كل البيانات إما ثابتة داخل الكود أو في `localStorage`، أي محصورة في متصفح واحد.
- معالِجان متعارضان لنموذج الدخول (في `login.html` وفي `js/app.js`).
- أزرار تعرض رسالة نجاح بلا حفظ: اعتماد القيد، تحديث المهمة/الطلب، بلاغ المفقودات، التقييم.
- محادثة وهمية برد آلي يحاكي «غرفة العمليات».

### قاعدة البيانات قبل المراجعة
| المشكلة | الأثر | الإصلاح |
|---|---|---|
| `ratings` بلا `ENGINE` ولا `CHARSET` | قد يتجاهل المفتاح الأجنبي أو يفسد العربية حسب إعدادات الخادم | `InnoDB` + `utf8mb4_unicode_ci` + قيد `CHECK` للنجوم |
| `chat_rooms` بلا نص رسالة/مرسل/وقت | المحادثة غير قابلة للتشغيل | جدول `messages` + تحويل الغرفة لجماعية |
| `notifications` بلا مستقبِل | لا يمكن معرفة لمن التنبيه | `target_role`, `target_section`, `pilgrim_id`, `is_read` |
| لا جدول للقيود المالية | 3 صفحات بلا مصدر بيانات | جدول `expenses` |
| حقول التسجيل بلا أعمدة | الجنس/البريد/الحالة/الأمراض تضيع | أعمدة في `pilgrims` |
| تخصص المشرف من آخر رقم في عضويته | تغيير الوظيفة يتطلب تغيير الرقم | جدول `jobs` + `supervisors.job_id` |
| `ratings` مرتبط بطلب محدد فقط | نافذة التقييم تقيّم خدمة عامة | `ratings.pilgrim_id` + `ratings.service_id`، و `provision_id` اختياري |
| لا توجد كلمة مرور لمدير الحملة | لا يمكن تسجيل دخوله | `campaigns.password_hash` |

### الموقع بعد المراجعة
- 18 صفحة تقرأ وتكتب من قاعدة البيانات عبر `api/` (الدخول، التسجيل، الملف الشخصي،
  التوزيع، لوحة الإدارة، لوحة المشرف، القيود، التنبيهات، المحادثة، ملف الحملة، ملف
  المشرف، الخدمات، الثقافي، السحب، السكن، الجدول، الخروج).
- لم يتغير `css/style.css` ولا تصميم أي صفحة. التغييرات في أكواد JavaScript داخل
  الصفحات، وإفراغ الصفوف التجريبية الثابتة من الجداول، وبناء تبويبات المحادثة
  وقوائم الخدمات والمشرفين من قاعدة البيانات.

### تطبيق الجوال: ما وُجد وما عُدِّل

التطبيق واجهة Flutter تعمل ببيانات تجريبية مكتوبة داخل الشاشات (وهذا مكتوب صراحة
في عدة شاشات منه)، **وغير متصل بقاعدة البيانات** — لا يحتوي حزمة `http` أصلاً.
المراجعة ركّزت على الشعار والتنقل والتوافق مع الموقع:

| ما وُجد | التعديل |
|---|---|
| لا يوجد `lib/main.dart`؛ نقطة الدخول كانت في `lib/app/main.dart` وإعدادات التشغيل تشير لملف غير موجود | أُنشئ `lib/main.dart` يحتوي `main()` و `RifqaApp` (نُقلا كما هما)، وبقيت شاشة الدخول في `lib/app/main.dart` |
| شعار مختلف عن شعار الموقع (نسخة أقل جودة وبتخطيط مغاير) | استُبدل `assets/images/logo.png` بنفس شعار الموقع |
| شاشة الدخول واللوحات تستخدم أيقونة مسجد عامة بدل الشعار | وُضع الشعار في شاشة الدخول وفي ترويسة اللوحات الثلاث داخل إطار دائري أبيض مع `BoxFit.contain` حتى لا يتمدد |
| أيقونة التطبيق واسمه على الجهاز هي أيقونة Flutter الافتراضية و «flutter_application_1» | أيقونات `mipmap` الخمس مولَّدة من الشعار مع هامش أبيض، والاسم «رفقة بلاد الحرمين» |
| شرط الدخول «10 أرقام بالضبط» يرفض أرقام الموقع وقاعدة البيانات (`100101`، `5000`، `30089`) | صار 4–12 رقماً مع نفس قاعدة البادئات، ونص القواعد مطابق للموقع |
| القسم مطلوب حتى لمدير الحملة | صار مطلوباً للحاج والمشرف فقط، كما في الموقع |
| صفحتا `medical_page` و `culture_page` موجودتان ولا يوصل لهما زر | زر «الخدمات الطبية» و «الثقافة والفعاليات» في لوحة الحاج يفتحانهما |
| صفحات إدارة الحجاج والمشرفين والخدمات موجودة ولا يوصل لها زر (كانت كل البلاطات تفتح قائمة نصية عامة) | ثلاث بلاطات في لوحة المدير تفتح الصفحات الفعلية |
| شاشة المحادثة تقارن الدور بـ «الحاج» و «المشرف» بينما اللوحات ترسل «حاج» و «مشرف»، فكان الحاج والمشرف يريان قائمة المدير | تصحيح المقارنة؛ وصار الدور يتبع القسم (حاجة / مشرفة) |
| لوحة المشرف تعرض التخصصات الأربعة لأي مشرف | تُعرض أقسام تخصصه فقط حسب نفس قاعدة الموقع (آخر رقم)، والمشرف العام `5000` يرى الكل |
| مسميات المشرفين في التطبيق («المشرف الطبي»، «مشرف التغذية»…) تختلف عن جدول `jobs` | وُحِّدت مع قاعدة البيانات: الموظف الصحي، موظف الحشود والتنقل، موظف الإعاشة والأطعمة، موظف السكن وخدمة الحجاج |
| ملفان يستوردان نفسيهما، وخمسة ملفات غير مستخدمة من نسخة أقدم (`login_screen`, `welcome_page`, `home_screen`, `models/app_user`, `styles/app_styles`) | حُذف الاستيراد الذاتي والملفات غير المستخدمة؛ لا يوجد مسار في التطبيق كان يصل إليها |
| رقم العضوية المكتوب ثابتاً داخل المحادثة | يُمرَّر رقم العضوية الحقيقي من شاشة الدخول إلى اللوحات والمحادثة |

**ما لم يُنفَّذ في التطبيق عمداً:** ربطه بقاعدة البيانات. يحتاج إضافة حزمة `http`
وطبقة طلبات تتعامل مع نفس ملفات `website/api/` (التي ترجع JSON وتصلح له كما هي)،
وهذا خارج نطاق المراجعة الحالية. البيانات التجريبية داخل شاشاته مكتوب تحتها أنها
تجريبية ولم تُقدَّم على أنها حقيقية.

## 8. توافق عناصر المشروع مع بعضها

| العنصر | الحالة |
|---|---|
| أنواع المستخدمين (حاج / مشرف / مدير) | متطابقة في الموقع والتطبيق وقاعدة البيانات |
| قاعدة أرقام العضوية `100 / 500 / 5000 / 300` | متطابقة بعد تعديل شرط الدخول في التطبيق |
| مسميات وظائف المشرفين | متطابقة: `jobs.job_title` = شاشات الموقع = شاشات التطبيق |
| الخدمات (طبي، تفويج، إعاشة، سكن، مفقودات) | متطابقة بين `services` والموقع وصفحات التطبيق |
| الشعار | ملف واحد في الموقع والتطبيق |
| مخطط ER | مولَّد من ملف SQL النهائي نفسه (`docs/er_diagram.png`) فهو مطابق بالضرورة |
| البوستر والهدف الرئيسي | **لم تتوفر ملفاتهما ضمن ما استُلم**، فلم تتم مقارنتهما. عند توفرهما تُقارَن قائمة الخدمات والمستخدمين فيهما بالجدول أعلاه |

نقاط يجب الانتباه لها عند العرض:
- الموقع متصل بقاعدة البيانات فعلياً؛ التطبيق واجهة عرض ببيانات تجريبية. يجب قول ذلك
  بوضوح وليس العكس.
- `permissions` = تصاريح الحج، و `jobs` = صلاحيات/وظائف النظام.

### ملاحظة مهمة عن طريقة الاختبار

اختبارات الـ API والمتصفح أعلاه أُجريت مع **تشغيل نفس ملفات PHP على قاعدة SQLite
كبديل** لعدم توفر خادم MySQL في بيئة الاختبار. هذا يختبر منطق PHP وأسماء الأعمدة
والجلسات والصلاحيات والواجهة بالكامل، لكنه **ليس استيراداً فعلياً على MySQL**.
توافق ملف SQL مع MySQL فُحص بمحلل لغوي فقط.

### ما لم يُختبر
- استيراد `rafqa_haramain_final.sql` فعلياً في phpMyAdmin على MariaDB/MySQL.
- رفع صورة فاتورة حقيقية من المتصفح.
- زر تصدير Excel (مكتبة SheetJS تُحمَّل من الإنترنت).
- الوصول للموقع من جهاز آخر على نفس الشبكة.
- بناء التطبيق وتشغيله (`flutter run`) — لم يتوفر Flutter SDK في بيئة المراجعة،
  فالتعديلات في Dart رُوجعت يدوياً ولم تُترجَم.
- البوستر وملف الهدف الرئيسي لعدم توفرهما.

### متطلبات خارجية لازمة للتشغيل
- XAMPP (Apache + MySQL/MariaDB + PHP 8) وإنشاء قاعدة `rafqa_haramain` بترميز
  `utf8mb4_unicode_ci` ثم استيراد `website/sql/rafqa_haramain_final.sql`.
- `website/api/config.php` مضبوط على إعدادات XAMPP الافتراضية (`root` بدون كلمة مرور)؛
  يُعدَّل فقط إذا كانت إعدادات MySQL مختلفة.
- Flutter SDK لبناء التطبيق، ثم `flutter pub get`.
